## 1. 모델을 줄이고 토큰을 늘리세요 — `dim=768, L=12`

### 문제

```
현재:  N = 426,806,356   D = 528,905,026   D/N = 1.24
```

Chinchilla 최적은 D/N ≈ 20입니다. 지금은 **1.24**입니다.

이걸 다르게 표현하면 이렇습니다. 현재 크기를 제대로 학습시키려면 **8.5B 토큰**이 필요하고, 보고된 학습 처리량(RTX 5060 Ti에서 2,033 tok/s) 기준으로 **48.6일**이 걸립니다. 즉 **가진 하드웨어로 학습할 수 없는 크기의 모델을 만든 것**입니다. 그래서 1.24에서 멈출 수밖에 없었고, 지금 보이는 약점 대부분이 거기서 나옵니다.

### 계산

현재 학습 컴퓨트를 그대로 두고(`C = 6ND = 1.354e18 FLOPs`) Chinchilla 최적점을 풀면:

```
N* = 106,240,300     D* = 2,124,806,000
```

릴리스의 `ModelConfig`/`build_model`로 실제 파라미터를 세어 후보를 뽑았습니다.

| config | 파라미터 | N* 대비 | 필요 토큰(20×) | 예상 학습 시간 |
|---|---:|---:|---:|---:|
| dim=1216 L=20 (현재) | 426,806,356 | 4.02× | 8.54B | 48.6일 |
| dim=1024 L=16 | 252,226,576 | 2.37× | 5.04B | 17.0일 |
| dim=896 L=16 | 197,711,760 | 1.86× | 3.95B | 10.4일 |
| dim=768 L=16 | 147,424,016 | 1.39× | 2.95B | 5.8일 |
| **dim=768 L=12 H=12** | **115,827,468** | **1.09×** | **2.32B** | **3.6일** |
| dim=640 L=12 | 84,218,764 | 0.79× | 1.68B | 1.9일 |
| dim=512 L=12 | 57,558,028 | 0.54× | 1.15B | 0.9일 |

학습 시간은 처리량이 파라미터 수에 반비례한다고 보고 추정한 값입니다. 실제로는 더 걸리겠지만 자릿수는 맞습니다.

### 권고

**`dim=768, n_layers=12, n_heads=12`.** 115.8M 파라미터로 최적점의 1.09배, 2.3B 토큰, 사흘 반이면 끝납니다.

`anchor_layer_indices`는 `[0,2,4,6,8,10]`으로 두어 지금의 격층 패턴을 유지하세요. `num_anchors=256`, `router_dim=256`, `top_k=8`은 그대로 두는 걸 권합니다 — 한 번에 한 변수만 바꿔야 원인을 알 수 있습니다.

빠른 반복이 필요하면 **dim=640, L=12**(1.9일)로 먼저 파이프라인을 돌려보고 확신이 서면 768로 가는 것도 좋습니다.

> 작은 모델이 지금 것보다 성능이 좋을 가능성이 높습니다. 지금 426M이 GPT-2 124M에게 BPB로 지고 있는데, 그건 크기가 부족해서가 아니라 학습이 부족해서입니다.

## 2. 품질 축 대조군을 만드세요

지금 아키텍처 주장은 **속도 축에만** 있습니다(`TECHNICAL_OVERVIEW.md`의 매칭 벤치마크). 품질 축 대조군이 없어서 정작 핵심 질문에 답을 못 합니다: **"FDT가 언어모델링에 쓸 만한 아키텍처인가?"**

**해야 할 일**: 1번에서 정한 설정으로 학습할 때, **완전히 동일한 조건**의 dense transformer를 하나 더 학습하세요.

- 같은 토크나이저, 같은 데이터, 같은 토큰 수, 같은 옵티마이저, 같은 스텝 수
- 파라미터 수를 맞출 것(±1% 이내). 이미 426M에서 해봤으니 방법은 알고 있을 겁니다
- 비교 지표는 **held-out BPB**. perplexity가 아니라 BPB여야 나중에 외부 모델과도 비교됩니다

이 실험 하나가 이 프로젝트 전체의 존재 이유를 결정합니다. 지금까지 나온 모든 수치보다 가치 있습니다.

## 3. 반복 붕괴 — 이미 절반은 해결했습니다

### 발견한 것

먼저 버그가 있었습니다. **`repetition_penalty`가 1.0 초과일 때 크래시했습니다.**

```
cuda/float32   penalty=1.15  FAIL  RuntimeError: Inplace update to inference tensor...
cuda/bfloat16  penalty=1.15  OK
cpu/float32    penalty=1.15  FAIL
```

`prefill`/`decode_step`이 `@torch.inference_mode()`라 로짓이 inference tensor인데, `.float()`가 이미 fp32면 no-op이라 원본을 그대로 반환합니다. 거기에 in-place 쓰기를 하니 터집니다. **CPU는 원래부터 fp32라 원본 릴리스에서도 깨져 있었습니다.** CLI·API·웹 UI에 모두 노출된 기능이 100% 실패하고 있었습니다. `logits.clone()` 한 줄로 고쳤습니다.

### 그리고 고쳤더니 드러난 진짜 문제

페널티가 반복은 잡는데 **정확 복사를 깨뜨립니다.**

| penalty | 반복률 | retrieval | JSON |
|---:|---:|---|---|
| 1.00 | 0.463 | OK | OK |
| 1.10 | 0.279 | **깨짐** | OK |
| 1.25 | 0.022 | **깨짐** | OK |
| 1.50 | 0.000 | **깨짐** | **깨짐** |

당연합니다. 구현이 `torch.unique(generated)`로 **프롬프트 토큰까지** 페널티를 먹입니다. 그런데 retrieval은 프롬프트에 있는 식별자를 그대로 복사하는 과제입니다. 즉 **모델이 해야 할 일을 정확히 억제하고 있었습니다.**

### 해결

페널티를 **생성된 토큰에만** 적용하도록 `repetition_scope` 옵션을 추가했습니다(기본값 `all`로 하위호환 유지).

| 설정 | 반복률 | retrieval | JSON |
|---|---:|---|---|
| penalty=1.00 | 0.463 | OK | OK |
| penalty=1.10 scope=all | 0.279 | 깨짐 | OK |
| **penalty=1.10 scope=generated** | **0.232** | **OK** | **OK** |
| penalty=1.15 scope=generated | 0.178 | OK | OK |

**반복률이 절반으로 떨어지면서 두 능력 모두 살아남습니다.** 지금 바로 쓸 수 있습니다.

```powershell
.venv\Scripts\python.exe infer.py --prompt "..." --repetition-penalty 1.10 --repetition-scope generated
```

### 남은 일 (학습 쪽)

추론 옵션은 증상 완화입니다. 근본 원인은 exposure bias로 보입니다. 가장 강한 증거:

| 버킷 | teacher-forced perplexity | 자유 생성 반복률 |
|---|---:|---:|
| code_python | **6.5** (가장 좋음) | **0.666** (가장 나쁨) |

**가장 잘 학습된 영역에서 가장 심하게 무너집니다.** 정답이 앞에 깔려 있으면 잘하고, 자기 출력을 먹기 시작하면 궤도를 벗어납니다.

다음 학습에서 시도할 것:
- EOS 감독 강화 (이미 시도했다고 적혀 있으니 강도를 올려보세요)
- scheduled sampling 계열 — 학습 중 일부 스텝에서 정답 대신 모델 출력을 먹이기
- completion 길이 상한을 더 짧게. 지금 Python 샘플이 192토큰까지 가면서 무너집니다

## 4. 위치 임베딩을 RoPE로

`use_rope: false` + 학습된 절대 위치 임베딩이 컨텍스트를 2,048에 하드 고정합니다.

문제는 이겁니다. 자체 벤치마크에서 FDT가 dense를 이기는 지점이 2,048인데, 그것도 점근적 우위가 아니라 **dense가 VRAM 절벽에 부딪혀서**입니다. 즉 `O(N(K+W))`가 `O(N²)`를 실제로 이기기 시작하는 구간이 **모델 자신의 컨텍스트 한계 밖**에 있습니다. **아키텍처의 중심 주장을 이 모델로는 증명할 수 없습니다.**

RoPE로 바꾸면 학습 길이를 넘어서도 외삽이 되고, 8K·16K에서 재측정할 수 있습니다. 그 구간에서야 이 설계의 존재 이유가 숫자로 나옵니다.

2번(품질 대조군)과 함께 하면 좋습니다. 같은 실험에서 두 축을 다 볼 수 있습니다.

## 5. 평가 하네스 정리

지금 평가는 이미 상당히 좋습니다(행별 `correct_definition`, Wilson 구간, sealed holdout 아님을 명시). 세 가지만 더하면 됩니다.

1. **실행 조건 기록.** 근거 JSON에 `device`·`dtype`·`seed`·`max_new_tokens`·정지 규칙이 하나도 없습니다. 이게 없어서 지금 근거를 제3자가 재현할 수 없습니다(19건 중 13건만 일치). 런타임 쪽은 고쳐뒀으니 평가 스크립트에서도 같이 저장하세요.
2. **평가 스크립트 동봉.** 지금은 스크립트의 SHA-256만 있고 스크립트가 없습니다.
3. **BPB 지표 추가.** 자기 토크나이저 기준 perplexity만으로는 외부 모델과 비교가 안 됩니다. `sum(-log p) / ln(2) / len(text.encode('utf-8'))` 한 줄이면 매번 "GPT-2 대비 어디쯤"에 답할 수 있습니다.

## 6. 성능 최적화 (여유 있을 때)

이미 하나는 고쳐뒀습니다 — `scatter_add` → `scatter_add_`로 **prefill 1.4~1.6배** 가속(출력 비트 단위 동일). 남은 것:

**디코드가 디스패치 바운드입니다.**

```
1스텝당 aten 연산 호출  489회
  self CUDA               24.5 ms
  self CPU                33.0 ms   ← GPU보다 CPU가 오래 걸림
  GEMV(줄일 수 없는 하한)  10.3 ms
```

나머지 ~18 ms가 오버헤드입니다. batch를 4배 키워도 스텝 시간이 그대로인 것도 같은 신호입니다. CUDA Graphs로 디스패치를 캡처하거나 `torch.compile`로 anchor 스텝을 퓨전하면 2배 이상 여지가 있습니다. 다만 학습 코드와 얽혀 있어 1~4번을 끝낸 뒤에 손대는 게 맞습니다.
