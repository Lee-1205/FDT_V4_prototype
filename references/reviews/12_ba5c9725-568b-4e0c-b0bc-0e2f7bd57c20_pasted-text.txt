# FDT NEXT-GENERATION — FINAL VERIFICATION / AUDIT PROMPT

현재 private GitHub repository에 구현된 차세대 FDT 전체를 마지막으로 검수하라.

이 작업의 목적은 새로운 기능을 추가하는 것이 아니라,

1. 구현이 설계 의도대로 되었는지
2. 기존 FDT 핵심 구조가 손상되지 않았는지
3. Exact Memory가 실제로 lossless identity channel로 작동하는지
4. 자유 생성 반복 붕괴가 개선되었는지
5. RoPE/장문 컨텍스트가 실제로 정상 작동하는지
6. incremental FDT의 장문 decode cost 특성이 유지되는지
7. GPU 성능 측정이 실제 현재 연구 장비에서 재검증되었는지
8. 평가와 결과가 재현 가능한지

를 엄격하게 확인하는 것이다.

절대로 결과를 좋게 보이도록 기준을 바꾸지 말고,
실패하면 실패로 보고하라.

현재 repository는 PRIVATE 상태를 유지한다.
visibility를 변경하거나 public release를 만들지 마라.

============================================================

현재 FDT의 핵심 정체성은 유지되어야 한다.

기본 구조:

- causal language model
- local causal attention
- local window W=64
- fuzzy semantic anchors
- 256 anchors / anchor layer
- router_dim=256
- top-k=8
- cosine membership
- temperature=0.25
- 격층 fuzzy-anchor 구조

- Exact Episodic Memory

- repetition/generated stability 개선
- EOS/loop objective 개선
- long-context support
- runtime/kernel optimization

다음은 이번 검증 과정에서 새로 도입하지 마라:

- adaptive top-k

- 별도의 독립 specialist 모델
- 임의의 모델 축소

특히 FDT를 dense Transformer처럼 바꾸는 방식으로 문제를 해결하지 마라.

============================================================
3. RoPE 검증
============================================================

기존 learned absolute positional embedding이 실제로 제거되었는지 확인하라.

RoPE는 우선 local attention의 Q/K에 적용되어야 한다.

확인할 것:

- Q/K rotary 적용
- position offset이 incremental decode에서도 올바름
- cache decode position과 full recompute position이 동일
- chunk/stateful processing에서 position reset이 발생하지 않음
- fuzzy anchor router에 의도치 않은 RoPE rotation이 직접 적용되지 않음
- 2K를 넘는 position index가 정상적으로 처리됨

다음 context에서 smoke/integrity test:

512
1024
2048
4096
8192

가능하면:

16384

단, 16K가 현재 하드웨어 한계로 불가능하면 OOM을 숨기지 말고
정확한 peak VRAM과 실패 위치를 기록한다.

RoPE를 사용한다고 해서
"훈련 길이를 넘어도 무조건 일반화한다"고 가정하지 마라.

2K / 4K / 8K / 16K에서 실제 성능을 각각 측정한다.

============================================================
4. Fuzzy Semantic Memory 검증
============================================================

기존 FDT semantic state가 유지되어야 한다.

각 anchor layer에 대해 다음을 검사:

- numerator
- mass
- update ordering
- causal prefix exclusion
- long summary
- recent summary
- recency weighting
- selected anchor membership
- top-k sparsity
- cache state consistency

미래 token이 anchor state에 유입되는 causal leakage가 없어야 한다.

random small model에서:

full recompute

vs

incremental cached decode

를 비교한다.

FP32 integrity test를 canonical reference로 사용한다.

logit max absolute error,
token agreement,
anchor-state agreement를 기록한다.

BF16 결과는 별도로 측정하되
FP32 결과와 혼동하지 않는다.

============================================================
5. Exact Episodic Memory는 필수 기능이다
============================================================

Exact Memory는 optional gimmick이 아니다.

FDT의 fuzzy semantic state가 의미적 관계를 담당하고,

Exact Memory가

- 숫자
- arbitrary alphanumeric sequence
- UUID-like sequence
- hash-like sequence
- identifiers
- quoted values
- JSON scalar values
- code identifiers/signatures
- 의미가 거의 없는 문자열

의 정확한 identity를 보존하도록 설계되었다.

원칙:

Meaning = Fuzzy
Identity = Exact

구현이 이 원칙과 일치하는지 검사하라.

============================================================
6. Exact Memory 내부 구조 검증
============================================================

Exact Memory가 raw token ID를 lossless하게 저장하는지 확인한다.

검사:

- token append
- position/span metadata
- chunk boundary
- anchor index/posting
- candidate retrieval
- reranker
- exact-need gate
- copy distribution
- copy cursor
- cursor termination
- generation 복귀

Exact Memory가 hidden representation만 저장하고
원래 token identity를 버리는 방식이면 FAIL이다.

Exact Memory search가 매 decode마다
전체 context O(N)을 scan하는 구조이면 FAIL/WARNING이다.

기존 fuzzy top-k routing을 1차 index로 재사용하는 것이 기본 설계다.

candidate chunk 수에는 bounded cap이 있어야 한다.

Copy Mode에서 repetition penalty 때문에
정답 token이 억제되어서는 안 된다.

19. FDT compute claim 검증
============================================================

다음 주장을 별도로 구분한다.

A. algorithmic interaction/state scaling
B. real GPU wall-clock

FDT의 intended long-context shape:

O(N(W+K))

은 interaction/state access 관점의 가설이다.

전체 모델 FLOPs가 O(72N)이라는 식으로 과장하지 마라.

router가 256 anchors를 scoring하는 비용,
MLP,
projection,
kernel overhead도 별도로 존재한다.
