가장 유력한 해결책은 **현재 FDT의 의미 앵커를 없애거나 더 크게 만드는 게 아니라, 앵커 옆에 “손실 없는 exact-memory 경로”를 하나 추가하는 것**이라고 봅니다.

현재 보고서에서 실제 병목도 정확히 이쪽입니다. 숫자·식별자·JSON 값 같은 정보를 그대로 보존하는 능력이 약하고, `Q7M2X9K4P8V3N6L1`을 `Q6M2X9K5`처럼 비슷하지만 다른 문자열로 생성하는 현상이 관찰됐습니다. 

## 핵심 아이디어: 앵커는 “기억”이 아니라 “주소”도 저장한다

지금 구조는 대략 이렇습니다.

```text
과거 token
    │
    ▼
fuzzy membership
    │
    ▼
Anchor numerator / mass
    │
    ▼
의미 summary
```

이 방식은 의미를 압축하기에는 좋지만,

```text
Q7M2X9K4P8V3N6L1
```

같은 정보에는 치명적입니다.

`Q7`, `M2`, `X9`의 **정확한 순서 자체가 정보**인데, 여러 hidden representation을 평균·누적하는 순간 그 순서와 원본 token ID를 완전히 복원할 방법이 없어질 수 있기 때문입니다.

그래서 저는 다음처럼 바꾸는 게 가장 좋다고 봅니다.

```text
                   ┌─ Semantic Memory
Past Token ────────┤  numerator / mass
                   │  의미 압축
                   │
                   └─ Exact Memory
                      raw token IDs
                      위치 / span 주소
```

그리고 fuzzy anchor는 두 가지 역할을 합니다.

```text
Anchor = 의미 요약
       + 원본 정보가 어디 있는지 가리키는 색인
```

즉 **“내용을 전부 기억하는 서랍”이 아니라 “요약 + 원본 문서 위치가 적힌 색인카드”**가 되는 겁니다.

---

# 1. 원본 토큰 자체는 놀랄 정도로 싸게 저장할 수 있음

이게 중요한 포인트입니다.

기존 Transformer의 KV cache가 비싼 이유는 각 token마다 수백~수천 차원의 K/V vector를 보관하기 때문입니다.

그런데 exact memory에는 그럴 필요가 없습니다.

그냥:

```text
token_id
position
```

만 보존하면 됩니다.

예를 들어:

```text
Position 1034 → token 583
Position 1035 → token 21
Position 1036 → token 9182
...
```

입니다.

token ID를 `int32`로 저장한다고 단순 계산하면:

- 2,048 tokens → 약 8 KB
- 100,000 tokens → 약 0.4 MB
- 1,000,000 tokens → 약 4 MB

정도밖에 안 됩니다.

물론 실제 구현에는 position/index/chunk metadata가 추가되지만, **전체 hidden/KV를 저장하는 것과는 차원이 다르게 작습니다.**

따라서 FDT가 줄이려던 것은

> “과거의 거대한 K/V 표현 전체”

이지,

> “몇 바이트짜리 원본 token ID”

까지 버릴 필요는 없습니다.

---

# 2. 그래서 구조를 이렇게 만들 수 있음

제가 가장 추천하는 구조는 일단 이름을 붙인다면:

**FDT Dual Memory**

정도로 볼 수 있습니다.

```text
                         ┌──────────────────┐
                         │ Semantic Memory  │
                         │ 256 Fuzzy Anchor │
                         │ numerator / mass │
                         └────────┬─────────┘
                                  │
Past tokens ──────────────────────┤
                                  │
                         ┌────────▼─────────┐
                         │   Exact Memory   │
                         │ raw token buffer │
                         │ + positions      │
                         └────────┬─────────┘
                                  │
                                  ▼
                            Current Token
```

다만 exact memory를 매번 전부 검색하면 다시 비싸집니다.

그래서 **semantic anchor를 검색 인덱스로 사용**합니다.

---

# 3. Anchor에 문자열 자체를 넣지 말고 위치를 연결한다

예를 들어 과거 문장이:

```text
암호 코드는 Q7M2X9K4P8V3N6L1이다.
```

였다고 합시다.

현재 FDT에서는 이 문장이 hidden representation으로 변환되어 anchor들에 퍼지하게 누적됩니다.

새 방식에서는 동시에:

```text
Exact token buffer

...
[821] "Q"
[822] "7"
[823] "M"
[824] "2"
...
[836] "1"
```

같은 원본을 그대로 유지합니다.

그리고 해당 문장이 강하게 연결된 anchor에는:

```text
Anchor 17
Semantic summary:
    [현재 방식의 numerator/mass]

Exact references:
    span 815~837
    span 1290~1304
    ...
```

같은 **주소**를 추가합니다.

Anchor 17 자체는 여전히 fuzzy semantic anchor입니다.

단지 이제:

> “나와 관계된 정확한 원본 정보가 저기에 있다.”

라는 포인터도 갖습니다.

---

# 4. 질문이 들어오면 먼저 의미로 찾고, 그다음 원본을 읽음

나중에:

> 암호 코드가 뭐였지?

라는 입력이 들어온다고 합시다.

현재 방식:

```text
질문
 ↓
Anchor 17, 43, 81...
 ↓
압축된 summary
 ↓
"아마 Q6M2..."
```

새 방식:

```text
질문
 ↓
Fuzzy routing
 ↓
Anchor 17 선택
 ↓
Anchor 17의 exact-reference 확인
 ↓
span 815~837 검색
 ↓
Q7M2X9K4P8V3N6L1
```

이렇게 됩니다.

핵심은:

> **의미는 fuzzy하게 찾되, 찾은 정보는 fuzzy하게 복원하지 않는다.**

입니다.

이게 FDT 철학과도 꽤 잘 맞습니다.

---

# 5. 마지막 출력에는 Copy Head를 추가

여기서 한 단계 더 가야 합니다.

원본 token을 찾았는데도 마지막 LM head가 다시

```text
hidden → vocabulary softmax
```

로 문자열을 재생성하게 만들면 또 틀릴 수 있습니다.

그래서 출력에도 별도의 **copy path**가 필요합니다.

```text
                    ┌─ Normal LM Head
Current hidden ─────┤
                    │
                    └─ Exact Copy Head
                           │
                           ▼
                       source token
```

최종적으로 모델이

\[
P(y)=gP_{\text{normal}}(y)+(1-g)P_{\text{copy}}(y)
\]

처럼 둘 사이를 선택하게 합니다.

비슷한 원리는 기존 연구의 pointer/copy mechanism에서도 사용된 적이 있습니다. Pointer Sentinel Mixture Model은 일반 vocabulary softmax와 context에서 단어를 직접 복사하는 pointer 경로를 혼합합니다. 

하지만 **FDT에서는 이걸 anchor memory와 결합한다는 점이 핵심 차이**가 됩니다.

---

# 6. 긴 문자열은 첫 글자마다 다시 검색할 필요도 없음

예를 들어 모델이 source position 821을 찾았다고 합시다.

```text
821 Q
822 7
823 M
824 2
825 X
826 9
...
```

첫 token에서:

```text
COPY_START = 821
```

을 결정하면 이후에는:

```text
821 → 822 → 823 → 824 → ...
```

순서대로 읽으면 됩니다.

즉 일종의 **copy cursor**를 둘 수 있습니다.

```text
Normal Mode
    │
    │ copy gate ON
    ▼
Copy Mode
source_pos = 821
    │
    ├─ output token[821]
    ├─ source_pos++
    ├─ output token[822]
    ├─ source_pos++
    ...
    │
    └─ COPY_END
            │
            ▼
       Normal Mode
```

그러면 긴 UUID, URL, 코드 identifier, 숫자열 같은 것은 모델이 매 토큰을 “기억해서 생성”할 필요조차 없습니다.

그냥 **원문을 읽어옵니다.**

---

# 7. 이것은 현재 Exact-Copy 병목과 정확히 맞물림

현재 보고서에서는:

- 비슷하지만 다른 identifier로 치환
- JSON key에 대응하는 값 변형
- Python 함수명/signature 변형
- sequence exact match 실패

가 핵심 문제로 정리되어 있습니다. 

이것들은 공통적으로 **“의미를 이해하는 것”과 “문자를 정확히 보존하는 것”이 다른 문제**입니다.

예를 들어:

```json
{"user_id":"A91X7K3"}
```

에서 FDT의 semantic memory가

```text
user_id = 어떤 알파뉴메릭 identifier
```

라는 의미를 잘 기억하더라도,

```text
A91X7K3
```

라는 값 자체는 그 의미만으로 복원할 수 없습니다.

그래서:

```text
Semantic channel:
"user_id라는 식별자가 존재한다"

Exact channel:
"A91X7K3"
```

를 분리하는 게 맞습니다.

---

# 8. 특히 좋은 점은 기존 Anchor를 버릴 필요가 없다는 것

저라면 **현재 numerator/mass 메모리를 절대 없애지 않습니다.**

왜냐하면 일반 언어의 대부분은 exact retrieval보다 semantic retrieval이 더 중요하기 때문입니다.

예:

> 철수는 어릴 때 부산에서 살았고 바다를 좋아했다.

나중에

> 철수는 해안 지역을 좋아했어?

같은 질문이 들어오면 exact token copy보다 의미적 요약이 더 중요합니다.

따라서:

```text
                 FDT Memory
                     │
          ┌──────────┴──────────┐
          │                     │
    Semantic Channel       Exact Channel
          │                     │
   fuzzy numerator/mass     token IDs
   의미 일반화             위치/순서 보존
          │                     │
          └──────────┬──────────┘
                     ▼
                 learned gate
```

가 가장 자연스럽습니다.

---

# 9. Anchor 자체에도 두 개의 Value를 둘 수 있음

조금 더 FDT다운 구현은 다음입니다.

각 anchor \(a_i\)에:

```text
Anchor_i
 ├─ semantic_state
 │    numerator
 │    mass
 │
 └─ exact_index
      chunk IDs / span references
```

를 둡니다.

즉:

\[
A_i=(S_i,E_i)
\]

입니다.

여기서

- \(S_i\) = fuzzy compressed semantic state
- \(E_i\) = exact-memory 위치 목록

입니다.

현재 token의 membership이:

```text
Anchor 17 = .51
Anchor 82 = .24
Anchor  3 = .13
...
```

라면 semantic path에서는 현재처럼 membership 가중합을 사용합니다.

그런데 exact path에서는:

```text
17에 연결된 span
82에 연결된 span
3에 연결된 span
```

만 후보로 가져옵니다.

즉 **top-8 anchor routing 자체가 exact memory의 검색량도 줄여주는 것**입니다.

---

# 10. 긴 context라면 token 단위보다 Chunk 단위 인덱싱 추천

모든 token position을 anchor마다 등록하면 index가 커질 수 있습니다.

그래서 예를 들어 16~32 token 단위 chunk로 만드는 방법이 더 좋습니다.

```text
Chunk 0 : tokens 0~31
Chunk 1 : tokens 32~63
Chunk 2 : tokens 64~95
...
```

각 chunk에는 작은 retrieval key를 하나 둡니다.

```text
Chunk
 ├─ key: 64~256 dimensional vector
 ├─ start_position
 └─ raw token IDs
```

Anchor에는 token 대신:

```text
Anchor 17 → chunk 5, chunk 91, chunk 204
```

처럼 연결합니다.

검색은:

```text
Current hidden
      ↓
Top-8 Anchors
      ↓
candidate chunks
      ↓
small reranker
      ↓
Top-2/4 chunks
      ↓
pointer/copy
```

가 됩니다.

이렇게 하면 전체 raw context에 attention할 필요가 없습니다.

외부 vector cache에서 관련 과거 state를 소수 검색하는 접근 자체는 Neurocache 같은 장문 LM 연구에서도 실험된 바 있습니다. 

---

# 11. 더 중요한 아이디어: 모든 정보에 Exact Memory를 쓰지 말 것

두 가지 선택지가 있습니다.

### 방법 A — 모든 raw token을 저장

제가 우선 실험에서는 이걸 추천합니다.

왜냐하면 raw token ID 자체가 매우 작기 때문입니다.

장점:

- detector 필요 없음
- 어떤 문자열이 나중에 중요할지 미리 판단할 필요 없음
- exact-copy benchmark에 가장 명확함

### 방법 B — 모델이 “exact-worthy” span만 저장

예를 들어:

```text
1234567
A9XZ-722
"my_key"
function_name
192.168...
JSON value
```

같은 것만 저장합니다.

`exactness gate`

\[
e_t=\sigma(W_eh_t)
\]

를 두고 높을 때 exact memory에 기록할 수도 있습니다.

하지만 저는 **초기 버전에는 추천하지 않습니다.**

왜냐하면:

> 저장하지 않은 정보는 나중에 절대로 복원할 수 없기 때문입니다.

먼저 모든 token을 저장해서 architecture가 실제로 exact-copy 문제를 해결하는지 확인한 뒤, 그 다음 selective storage로 최적화하는 편이 낫습니다.

---

# 12. 반대로 별로 추천하지 않는 해결책

단순히 다음을 하는 것은 근본 해결책이 아닐 가능성이 큽니다.

### Anchor를 256 → 512로 증가

정보를 여전히 평균/누적한다면:

```text
정확한 순서 손실
```

문제는 남습니다.

### top-k 8 → 16

검색 폭만 넓어집니다.

exact token sequence를 보존하는 별도 채널이 생기는 것은 아닙니다.

### Local window 64 → 128/256

가까운 문자열에는 도움이 되지만,

```text
distance > window
```

가 되면 같은 문제가 다시 나타납니다.

### Exact-copy dataset만 대량 추가

이건 **필요하지만 단독 해결책으로는 부족할 수 있습니다.**

만약 architecture 내부에서 이미 정보가 손실된다면 decoder에게 아무리 정답을 요구해도 복원할 데이터가 없습니다.

현재 보고서도 teacher-forced cross entropy 개선이 sequence exact match를 보장하지 않는다고 명시합니다. 

---

# 13. 제가 실제로 만들 순서는 이렇게 권함

처음부터 복잡하게 하지 말고 **A/B 실험 가능한 최소 형태**로 가면 됩니다.

**V1에서는 `Raw Token Memory + Copy Pointer`만 추가**합니다. 기존 fuzzy anchor는 전혀 변경하지 않습니다. 각 token의 ID와 position을 저장하고, exact-copy 문제에서 source position을 직접 선택할 수 있는 pointer head만 붙입니다.

그 다음 **V2에서 Anchor-indexed retrieval**을 넣습니다. top-8 anchor가 관련 raw span 후보만 제시하도록 만들어 긴 context에서도 전체 memory를 검색하지 않게 합니다.

마지막으로 **V3에서 Semantic/Exact gate**를 넣어 일반 생성은 기존 LM head, 정확한 회수는 copy head로 자동 전환하게 합니다.

구조적으로는 최종적으로:

```text
                         ┌─ Local Attention (W=64)
                         │
Token hidden ────────────┼─ Fuzzy Semantic Memory
                         │      256 → top-8
                         │      numerator/mass
                         │
                         └─ Exact Episodic Memory
                                │
                         anchor-indexed spans
                                │
                              pointer
                                │
                        exact source tokens

                               ↓

                         Semantic / Copy Gate

                        ┌────────┴─────────┐
                        │                  │
                    LM Head           Copy Head
                        │                  │
                        └────────┬─────────┘
                                 ▼
                              Output
```

가 됩니다.

제가 보기에는 **Pure-FDT의 현재 구조적 장점을 가장 적게 훼손하면서 exact-copy를 해결할 가능성이 가장 높은 방향**입니다.

핵심 문장으로 줄이면:

> **Fuzzy Anchor에는 “무엇을 의미하는지”를 기억시키고, Exact Memory에는 “정확히 무엇이 쓰여 있었는지”를 기억시킨다. 그리고 Anchor가 Exact Memory의 주소를 찾게 한다.**

이렇게 하면 원래 FDT 철학인 **“모든 토큰끼리 직접 계산하지 않고 잠재 의미 앵커를 통해 관련 정보만 찾는다”**도 그대로 유지됩니다. 오히려 semantic anchor가 **압축 메모리인 동시에 lossless memory의 검색 인덱스**가 되므로 원래 아이디어와 더 자연스럽게 결합됩니다.
